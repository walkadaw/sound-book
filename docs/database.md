# База данных

MySQL 5.7, InnoDB. С базой работает только PHP API в `api/` (PHP 8.5), подключение в `api/classes/_class.db.php`, кодировка соединения `utf8mb4`.

| Таблица | Что хранит |
| --- | --- |
| `sound_list` | Песни: название, текст, аккорды, теги, счётчики использования |
| `sound_list_history` | Версии песен, сохранённые из админки |
| `sound_media` | Записи исполнения песен: YouTube, Google Drive, файлы |
| `liturgy` | Чтения дня, скачанные с catholic.by |
| `sound_user` | Учётные записи админки |
| `ad_options` | Служебные настройки, сейчас только версия списка песен |

Время везде в Unix-секундах (`int`), кроме `sound_list.time`.

## sound_list

Одна строка на песню. Таблица в `utf8` (3-байтовая), поэтому эмодзи и другие символы вне BMP в текст песни не сохранить.

| Колонка | Тип | Описание |
| --- | --- | --- |
| `id` | `int`, PK, auto increment | Номер песни. Его видят на сайте и в бумажном спеўніку, поэтому номера не переиспользуются |
| `title` | `varchar(120)` | Название в том регистре, в котором его ввели. Капслоком его делает только CSS (`.song-name`) |
| `text` | `text` | Текст песни, строки через `\n` |
| `chord` | `text` | Аккорды построчно: строка `N` в `chord` относится к строке `N` в `text`. Строка из одной точки `.` значит, что над этой строкой текста аккордов нет |
| `tag` | `varchar(55)` | ID тегов через запятую, например `1,3,10,`. Названия тегов хранятся не в базе, а в `src/app/constants/tag-list.ts` |
| `position` | `smallint unsigned`, null | Место части Імшы в литургии: песни с тегом «Часткі імшы» идут в конце списка по возрастанию `position`, за ними по алфавиту те, у кого `NULL`. У песен без этого тега не учитывается. В админке не редактируется, задаётся прямо в базе; после правки нужно обновить `ad_options.last_update`, иначе клиенты не получат новый порядок |
| `view` | `int`, default 0 | Сколько раз открывали песню |
| `showP` | `int`, default 0 | Сколько раз показывали песню в режиме презентации |
| `favorite` | `int unsigned`, default 0 | Сколько раз песню добавляли в избранное |
| `time` | `timestamp`, default `CURRENT_TIMESTAMP` | Время создания строки. API не использует |
| `type` | `tinyint`, default 0 | API не использует |

Индексы: `PRIMARY KEY (id)`, `FULLTEXT text (title, text)`. Поиск на сайте идёт на клиенте по скачанному списку, полнотекстовый индекс API сейчас не использует.

Счётчики `view`, `showP` и `favorite` клиент копит у себя и отправляет пачкой в `song/stats`. Обновление счётчиков не меняет `ad_options.last_update`, чтобы клиентам не приходилось заново скачивать список песен.

`song/get` отдаёт `tag` объектом `{"<id>": 1}`, а в `song/update` клиент присылает строку в формате колонки.

## sound_list_history

Версии песен. Пишет `song/update` (`api/song/_set_song.php`), читает `song/history`.

| Колонка | Тип | Описание |
| --- | --- | --- |
| `id` | `int unsigned`, PK, auto increment | Порядок версий: больший `id` = более поздняя версия |
| `song_id` | `int` | `sound_list.id`. Внешнего ключа нет |
| `title`, `text`, `chord`, `tag` | как в `sound_list` | Содержимое песни в этой версии |
| `user_id` | `int`, null | `sound_user.id` автора правки. `NULL` у исходной версии, сохранённой до появления истории |
| `created_at` | `int`, null | Когда версия создана |
| `updated_at` | `int`, null | Когда версию последний раз дополняли, `NULL` если не дополняли |

Индексы: `PRIMARY KEY (id)`, `KEY song_id (song_id, id)`.

Как появляются версии:

- Новая песня сразу получает первую версию.
- Если у песни, созданной до появления истории, ещё нет версий, при первой правке сначала сохраняется её прежний текст (с `user_id` и `created_at` = `NULL`), потом новый.
- Сохранения одного пользователя с промежутком меньше 10 минут (`HISTORY_MERGE_SECONDS`) не создают новую версию, а перезаписывают последнюю и обновляют `updated_at`.
- Сохранение без изменений версию не создаёт.

## sound_media

Записи исполнения песни, в порядке `position`. Пишут `song/media/save`, `song/media/delete`, `song/media/order`, читает `song/media`.

| Колонка | Тип | Описание |
| --- | --- | --- |
| `id` | `int unsigned`, PK, auto increment | |
| `song_id` | `int`, FK → `sound_list.id` `ON DELETE CASCADE` | Песня |
| `position` | `smallint unsigned`, default 0 | Порядок на странице песни, с 0. Новая запись встаёт в конец |
| `source` | `varchar(16)` | `youtube`, `gdrive`, `file` или `upload` |
| `ref` | `varchar(1024)` | Для `youtube` — ID видео из 11 символов, для `gdrive` — ID файла, для `file` — `https://` URL, для `upload` — имя файла в `api/media/`, загруженного в админке |
| `title` | `varchar(255)`, null | Название записи |
| `author` | `varchar(255)`, null | Исполнитель |
| `duration` | `smallint unsigned`, null | Длительность, секунды |
| `start_at` | `smallint unsigned`, null | С какой секунды играть, если песня — часть длинной записи |
| `end_at` | `smallint unsigned`, null | На какой секунде остановиться. Если задан вместе с `start_at`, то больше него |
| `created_at` | `int unsigned`, null | Когда запись добавлена |

Индексы: `PRIMARY KEY (id)`, `KEY song_position (song_id, position)`.

Таблица в `utf8mb4`, в отличие от остальных.

Записи из видео YouTube можно найти автоматически: `tools/video-songs/` готовит `INSERT` в эту таблицу.

## liturgy

Чтения дня на 15 дней вперёд, одна строка на каждую Імшу дня, у которой на catholic.by есть страница с текстами (будний день, успамін, Імша Хрызма и т. п.). Строки одного дня идут в порядке календаря, первая показывается по умолчанию. Таблицу пополняет cron-скрипт `api/liturgy/_parser.php`, раз в день в 00:15: удаляет дни раньше вчерашнего и скачивает дни с сегодняшнего по 14-й вперёд, которых в таблице ещё нет. Дни считаются по Минску. Тексты на catholic.by выкладывают вручную, обычно на месяц вперёд: если день там ещё не готов или не скачался, скрипт его пропускает и попробует на следующую ночь. Разобранную Імшу парсер проверяет (есть Евангелле, у чтений есть ссылка и «Чытанне…», в тексте нет заголовков секций, меток «Рэфрэн:» и слипшихся слов). Імша, не прошедшая проверку, молча пропускается, остальные Імшы дня записываются; если не прошла ни одна, день не записывается и скачивается снова на следующую ночь. Скрипт ничего не выводит. День записывается целиком в одной транзакции. Скачанный день больше не перекачивается: после изменения парсера таблицу очищают вручную (`DELETE FROM liturgy;`) и запускают скрипт, он разберёт все дни заново. `liturgy/get` отдаёт дни начиная со вчерашнего (устройство западнее Минска может быть ещё во вчерашнем дне) как объект `{"YYYY-MM-DD": [Імшы дня]}`. Фронтенд берёт день по дате устройства, а service worker хранит последний ответ до 15 дней: так чтения есть и без интернета. Слайды для презентации строит фронтенд: Імшу дня добавляют из поиска в меню презентации, в адресе она записывается как `l` (первая), `l2`, `l3`…

| Колонка | Тип | Описание |
| --- | --- | --- |
| `id` | `int`, PK, auto increment | Задаёт порядок Імшаў внутри дня |
| `date` | `date`, индекс | День, к которому относятся чтения |
| `artlitreadings` | `text` | Краткие ссылки на чтения из календаря catholic.by |
| `url` | `varchar(255)` | Адрес страницы catholic.by, с которой взяты тексты; на сайте ссылка на источник ведёт на неё |
| `title` | `varchar(255)` | Название Імшы |
| `sections` | `mediumtext` | JSON-массив секций `{type, title, reference, blocks, alternatives}`: `type` — `reading`, `psalm`, `sequence`, `acclamation`, `gospel` или `procession` (Евангелле працэсіі ў Пальмовую нядзелю). Только тексты литургического года этого дня. `blocks` — абзацы `{kind, lines}`, `kind` — `subtitle`, `intro` («Чытанне кнігі…»), `text`, `refrain`, `acclamation` (без меток «Рэфрэн:» / «Акламацыя:»), `rubric` (указания, справочная информация, в слайды не попадает) или `conclusion` («Гэта слова Божае»). `lines` — строки HTML, в которых остаются только `<b>` и `<i>`. `alternatives` — тексты `{reference, blocks}`, которые можно прочитать вместо первого (на catholic.by они идут после строки «або» / «альбо»), обычно пустой массив. Второй рэфрэн псалма — не альтернатива, а строка «Або: …» в блоке `refrain` |
## sound_user

Учётные записи админки. Дамп таблицы в репозиторий не кладём, здесь только колонки, которые использует API.

| Колонка | Описание |
| --- | --- |
| `id` | Попадает в сессию (`$_SESSION['user_id']`) и в `sound_list_history.user_id` |
| `username` | Логин и имя автора в истории версий |
| `password` | Хэш `password_hash()`. При входе хэш пересчитывается, если сменился алгоритм по умолчанию и новый хэш помещается в колонку |

## ad_options

Служебные настройки, одна строка с `id = 1`.

| Колонка | Описание |
| --- | --- |
| `last_update` | Unix-время последнего изменения песен. `song/update` ставит его при каждом сохранении. Клиент присылает свою версию в `song/get?last_update=`, и если она совпадает, получает `204` вместо списка. По этому же значению API сбрасывает кэш списка в `api/tmp/` |
